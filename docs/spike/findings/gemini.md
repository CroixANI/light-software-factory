# gemini slot, part A: E1–E5 (task 3.5, issue #18). Tested CLI: Antigravity `agy`

Evidence: [spike/gemini/](../../../spike/gemini/) (`run-agy.sh`, `agy.sb`, `hosts.sb`, `lsbind.sb`, `shell.sb`, `pty.sb`, `tokro.sb`, `login.sh`, `feed-code.sh`, `try.sh`). Plan: [../plan.md](../plan.md). Part B (E6–E12, S1–S5 re-run) is task 3.6 (issue #19) and is appended at the end of this file.

## Scope discrepancy (surprise, owner-confirmed)
The issue, the plan and the architecture say "Gemini CLI". The owner reported that **Google no longer supports the Gemini CLI** and installed and logged in the **Antigravity CLI (`agy`)** instead. On the owner's answer in this session, **`agy -p` (print/headless mode)** is what was tested for the gemini slot; the Gemini CLI (0.70.0 was still installed) was **not** exercised and its support status is as reported by the owner, not verified here. File names (`spike/gemini/`, `docs/spike/findings/gemini.md`) were kept as declared. Consequence for 4.1/4.2: the provider in the architecture's gemini slot has a different binary, different credential mechanism and different flags (below); the architecture and D-63's provider list need the owner's decision on the name and on whether "Gemini" stays as the provider id (not decided here, no `D-` entry created).

## Setup
- macOS 27.2.1 (arm64); `agy` 1.5.14, one native Mach-O file (~229 MB) at `~/.local/bin/agy` (not a directory: the profile grants exec and read on that **one file** only, `agy.sb`). It embeds a "language server" (Go) that starts inside the same process.
- Step folder from `build-step-folder.sh`, gateway from `connect-proxy.mjs` (allow-all, then allowlists). Profile: `base.sb` + `agy.sb` + the fragments listed below. Mach list: `com.apple.trustd.agent` only.
- Environment (empty + allowlist): `PATH=/usr/bin:/bin`, `HOME=<step>/home`, `TMPDIR=<step>/tmp`, `LANG`, `TERM=dumb`, `HTTP(S)_PROXY=http://127.0.0.1:<port>`, `FACTORY_STEP`. No agy-specific variable was needed (`agy` keeps everything under `$HOME/.gemini/` and `$HOME/Library/Application Support/antigravity/`).
- Model for all calls: `--model gemini-3.8-flash-low` (cheap; from `agy models`).
- **Baseline (owner-confirmed, not run by the agent):** outside the sandbox, with the real `HOME` and the login stored in the macOS Keychain, `agy -p Hello` works. The credential of that login lives only in the Keychain (service `gemini`, account `antigravity`; no token file under the real `~/.gemini`), so it **cannot be copied read-only into a Step**; the owner forbade copying it anyway.
- **Credential used for E1/E2 (no copy of the owner's login):** a fresh login done *inside* a sandboxed Step: `login.sh` runs `agy acp --login` under the profile (Keychain and `open` denied, so agy prints the URL and waits on stdin, no timeout seen over ~80 s); the owner opened the URL, and the one-time code was passed as a secret file and piped to agy's stdin (never printed). Result: agy wrote `$HOME/.gemini/antigravity-cli/antigravity-oauth-token` (0600, JSON with `access_token`, `refresh_token`, `expiry`, `expires_in` = 3599, `auth_method`, `id_token_email`). Log lines: `Failed keyring SaveToken, falling back to file` after `fork/exec /usr/bin/security: operation not permitted`. All Step folders and that file stay outside the repository and were deleted at the end of the session.

Commands (`R=spike/gemini/run-agy.sh`; `S` = step folder; gateway `connect-proxy.mjs --port 8931`; a 60–120 s limit via `perl -e 'alarm N; exec @ARGV'`; `X` = `--mach com.apple.trustd.agent --extra-sb hosts.sb --extra-sb lsbind.sb`):
- E1 sandboxed call: `$R --step $S --port 8931 $X -- -p "Reply with exactly: ok" --output-format json --model gemini-3.8-flash-low` (stdin `/dev/null`).
- E1 unsandboxed isolated-HOME check, no credential: `env -i PATH=/usr/bin:/bin HOME=$S/home … agy -p … --output-format json` (see "Procedure incidents").
- E3 credential-free probes: `… --env GEMINI_API_KEY=<fake> -- -p … --settings '{"modelProvider":"gemini"}'` (a fake key reaches `generativelanguage.googleapis.com` and gets `400 API key not valid`, which is enough to see TLS and network behaviour).
- E4: gateway with `--allow "<hosts>"` on a second port, and a run with a port nothing listens on (`--port 8999`).
- E5: `$R … $X --extra-sb shell.sb --extra-sb pty.sb -- -p "Use your shell tool to run: echo hello-from-shell …" --output-format json --model gemini-3.8-flash-low --dangerously-skip-permissions [--sandbox | --mode auto | --settings '{"enableTerminalSandbox":false}']`.
- E2: step with a read-only copy: `$R --step $S2 --port 8931 --ro-token <token file> $X -- -p …`.

## Results
| # | Result | Evidence |
|---|---|---|
| E1 Keychain-free credential | **pass, with a different credential route** | Inside the profile (Keychain Mach services never allowed, `/usr/bin/security` not exec-able) the call completes: `status: SUCCESS`, answer returned, `agy` log `ChainedAuth: authenticated via keyring` after the `security` call failed; agy logs its file-backed token store under the name "keyring" (the no-file run, which is "not logged in", shows the file is what authenticated). This run used the writable token file of the login Step; the read-only copy is shown in the E2 runs (same call succeeded with `tokro.sb` denying writes). The CLI has a **file token store** (`$HOME/.gemini/antigravity-cli/antigravity-oauth-token`) that it uses automatically when `security` is unavailable. **Caveats:** (1) the owner's own login is Keychain-only, so the factory needs its own login done through the sandboxed procedure above (once; the token file is then the credential, copied read-only into each Step); (2) an unsandboxed run with an isolated `HOME` and no file is "not logged in" (the Keychain item is not found when `HOME` differs), so the file is required in every Step; (3) whether the Keychain login of the owner and the in-Step login coexist indefinitely (token revocation behaviour of a second consent) was not measured. Other credential routes exist but were not used: `GEMINI_API_KEY` with `modelProvider: "gemini"` in settings, `AGY_ADC_AUTH` (Application Default Credentials). |
| E2 Credential refresh | **pass, measured** | Access token lifetime is 3599 s; the file holds a `refresh_token`. Control before expiry: read-only copy works, file unchanged. After the token expired (13:13:22Z), a Step with a **read-only copy** (`tokro.sb` denies writes to the file) and **no prior probe** completed its call: log `keyringAuth: loaded token … expired=true`, then `token refreshed, new expiry=<+1 h>` (contact with `oauth2.googleapis.com`), file hash unchanged, no write error. So the refresh happens **in memory per call** and needs `oauth2.googleapis.com` in the gateway allowlist; a Step does **not** need a writable token file, and `provider probe` is not required to keep Steps from failing. A writable run also refreshes and rewrites the file (new expiry); the stale read-only copy kept working after two refreshes elsewhere (the refresh token was not rotated or invalidated in ~1 h). Not measured: refresh-token lifetime beyond ~1 h (days), revocation, behaviour with many parallel Steps refreshing at once (they would each refresh independently from the same refresh token). |
| E3 Mach allowlist | **pass: one service** | Starting from none, the only Mach service the CLI needed is **`com.apple.trustd.agent`** (reason: TLS server-certificate verification; without it every HTTPS call fails `x509: OSStatus -26276`). `com.apple.trustd` alone, and `com.apple.SecurityServer` alone, did not help. Not Mach but needed: read of `/private/etc/hosts` (+ `resolv.conf`, `nsswitch.conf`, and stat of `/etc`) because Go resolves `localhost` from files (`lookup localhost: no such host` without it; `hosts.sb`), and `network-inbound` on `localhost:*` for the in-process language server's two random loopback ports (`listen tcp 127.0.0.1:0: listen: operation not permitted`; `network-bind` alone is not enough, `lsbind.sb`). **Conflict with S3 (open item for the owner):** this rule is in every shape, reviewer-readonly included, and lets the worker (and, in the builder shape, its shell tools, which inherit the profile) listen on **any** loopback port. A worker could squat a port the orchestrator later hands to another Step's gateway and receive that Step's proxied CONNECTs or block its gateway. [sandbox-s5.md](sandbox-s5.md) records the same cost for `dotnet test`; for agy it applies to every Step. It cannot be narrowed per process in SBPL. Mitigation ideas, none tested: never reuse or pre-announce gateway ports and bind the gateway port before the worker starts; run agy's language server on a fixed port that is known in advance (no flag found); or accept the risk. `com.apple.trustd.agent` is a Security-framework service (certificate trust evaluation), not Keychain access, so it does not conflict with the plan's "deny Keychain/security Mach services"; what it exposes (user trust settings) was not examined. Not needed: Keychain/`security`, launchd job submission, LaunchServices, Apple Events, pasteboard, `mach-register`, `iokit-open`, `ipc-posix` (all stay denied). Builder shape adds only non-Mach rules: exec of `/bin/zsh` (see E5) and the PTY device files (`shell.sb` also carries exec of `/bin/sh`, `/bin/bash`, `echo`, `id`, `cat` copied from claude's profile; their necessity for agy was not tested). `dotnet`/`node` Mach needs are in [sandbox-s5.md](sandbox-s5.md) (none). Sandbox denials are not readable via `log show`; additions were found by failure and re-tested for minimality (removal tests: `/etc/hosts` read, `network-inbound`, `com.apple.trustd.agent`, `/bin/zsh` exec and the `/dev/ptmx|ttys` file rules were each shown necessary by removing them; `resolv.conf`, `nsswitch.conf` and the `/etc` stat were granted together with `/etc/hosts` and **not** tested separately, so they may be unnecessary). |
| E4 Proxy compliance | **pass** | With direct egress denied by the profile (only the Step's gateway port), full calls succeed, so every connection that the CLI **needs** used `HTTPS_PROXY`. **Limit (as in claude.md):** under `(deny default)` any direct attempt (DNS, telemetry) is dropped silently and cannot appear in the gateway log, so this shows the profile blocks direct egress, not that the CLI never tries; no second source (denial trace, unsandboxed capture) was collected. The path `/oauth2/v2/userinfo` comes from agy's own error text, a CONNECT gateway sees only host and port. With nothing listening on the profile port the CLI fails closed (`model … is not recognized as a known model`: its model-list fetch cannot connect). Hosts contacted (gateway log): `daily-cloudcode-pa.googleapis.com`, `aicode.googleapis.com`, `www.googleapis.com` (`/oauth2/v2/userinfo`, an "Eligibility check": **blocking it fails the call**), `oauth2.googleapis.com` (refresh/login), `play.googleapis.com` (telemetry, **blockable**: denied, call still succeeded), `lh3.googleusercontent.com` (account avatar, **blockable**). `generativelanguage.googleapis.com` is contacted only on the API-key route. The unsandboxed first run also contacted the CLI auto-updater service (`antigravity-cli-auto-updater-…run.app`); inside the profile the updater skips itself (`Directory … is not fully accessible … skipping update`), an accident of the profile, not a documented switch. Verified **sufficient** allowlist: a full call succeeded with exactly `daily-cloudcode-pa.googleapis.com, aicode.googleapis.com, www.googleapis.com, oauth2.googleapis.com` allowed and `play.googleapis.com` and `lh3.googleusercontent.com` denied. Individually shown necessary: `www.googleapis.com` (denied → call fails) and `oauth2.googleapis.com` (the refresh in E2). `daily-cloudcode-pa` and `aicode` were not denied one by one (the former is the model endpoint, the latter's role is unknown); treat them as required. |
| E5 Own sandbox off | **pass (default is off); pin it** | agy has its own "terminal sandbox" (documented: `sandbox-exec`/Seatbelt on macOS) controlled by settings `enableTerminalSandbox` (default `false`), `agentMode` (`auto` turns it on where offered), flag `--sandbox` (on) and `--mode auto`. In headless mode, default flags: the terminal tool ran `echo hello-from-shell` with **no sandbox log line** and no nesting. `--sandbox` logs `Print mode: enabling terminal sandbox for this session` and the command still ran; the home, repo and outside-write probe gave the same results as default under our outer profile (only a file-write probe was used, not a network probe, so whether a nested Seatbelt was really applied is **unknown**; do not pass it). `--mode auto` is "unavailable" for this account (`rollout flag off`) and falls back to default. `--settings '{"enableTerminalSandbox":false}'` also works. Tool approval: without `--dangerously-skip-permissions` headless mode **auto-denies** a command that has no `permissions.allow` rule (`command(<target>)` in settings) and says so on stderr (so approval gating exists in `-p`). **Not shown:** whether `permissions.allow`/deny rules still apply when `--dangerously-skip-permissions` is passed (it auto-approves "all tool permission requests"), nor that an allowed command runs without the flag; every shell-tool run here used the flag. Part B must test an allow-rule run without the flag and a deny case before the adapter can rely on allow/deny. ## Other findings
- **Terminal tool needs a PTY and `/bin/zsh`** (builder shape only): `failed to create PTY: operation not permitted` and `fork/exec /bin/zsh: operation not permitted` (it ignores `SHELL=/bin/sh`). Minimal rules: `file-read* file-write* file-ioctl` on `/dev/ptmx` and `/dev/ttys[0-9]+` (`(allow pseudo-tty)` alone does not help) and exec of `/bin/zsh` (`pty.sb`, `shell.sb`). **Cost of the PTY rule:** the regex matches every pseudo-terminal on the machine, including the owner's own terminal sessions (owner-owned, mode 620), so a builder worker could read keystrokes from or write escape sequences into another terminal. It was not narrowed (the Step cannot know its ttys in advance); open for the adapter/§5.
- **Instruction files are read (B1, noted for part B):** the planted `AGENTS.md` and `GEMINI.md` canaries were echoed back in the answers of every run in `repo/`. They must be excluded from the copy; E8 (part B) will list all files.
- **Headless output is already typed:** `--output-format json` gives `status`, `response`, `usage.{input_tokens, output_tokens, thinking_tokens, cache_read_tokens, total_tokens}`, `duration_seconds`; `--json-schema` exists; errors print a structured `AGY_ERROR: {…}` line on stderr (part B: E6, E7, E12). No cost field was seen.
- The CLI writes a lot under `$HOME/.gemini/` (conversation databases, a `brain/` transcript per run, built-in skills unpacked on first run, a log per run) and also `$HOME/Library/Application Support/antigravity/` (plugin secrets file). All of it lands in the Step's `home/`; nothing outside it was writable.
- Models are listed with `agy models`; effort is part of the model id (`…-low|medium|high|xhigh`) and `--effort` exists too, so the plan's "effort n/a" does not apply as written (part B to confirm).
- **The token file is readable by the agent's own tools** (builder shape): the read-only copy prevents modification, not reading. With `/bin/cat` or the shell allowed, a worker can read `antigravity-oauth-token` (access + refresh token + account name) and write it into `repo/` or `io/out`, from where it leaves through the normal output path (a PR). Not tested here (claude's part B measured that its token is not visible to the Bash tool; nothing equivalent was measured for agy). Part B item: test whether agy's terminal tool can read the file, and whether `home/` can be excluded from the worker's readable set or the file put out of the tool's reach (for the reviewer-readonly shape there is no shell). A refresh token also lives longer than the Step.
- Language-server ports: while the CLI runs, loopback ports are open to any local process (E3 cost). Whether they require the CSRF token (`ANTIGRAVITY_CSRF_TOKEN` appears in the binary) was not tested.

## Procedure incidents (reported to the owner in the session; recorded as surprises for the handoff)
1. **A login window opened on the owner's machine.** My first E1 baseline ran `agy -p` **without the sandbox** under an isolated `HOME` and empty environment. With no credential agy opened the system browser to the Google sign-in page. No credential was involved, but that run should have been inside the profile from the start. After the owner's instruction every later `agy` run used the profile (Keychain, `open` and LaunchServices denied) with an isolated `HOME`.
2. **Keychain was enumerated twice** with `security dump-keychain` (no `-d`: names and attributes only, no secret values) to find where the login lives (service `gemini`, account `antigravity`). The owner had allowed only "do not copy the credential", not enumeration. Stopped on instruction; no secret value was read.
3. `agy models` and `agy changelog` ran once each with the owner's real `HOME` (read-only listing calls).
4. The login output printed the owner's account name to the agent's tool output (not into any file in the repository; the Step folders were deleted).

## Verdict for part A (superseded by the final verdict after part B)
E1, E2, E3, E4, E5 **pass** for `agy -p` with: a Step-local file token produced by an in-sandbox login, `com.apple.trustd.agent` as the only Mach service, a four-host gateway allowlist, and `enableTerminalSandbox:false`. No part-A condition for `unsupported` is met, but the loopback-listen rule conflicts with S3 (see E3) and the owner must accept or reject that risk before the verdict is final. Open for the owner and part B: (a) the provider is `agy`, not the Gemini CLI; (b) the factory needs its own one-time sandboxed login (a `factory` "auth" step) because the owner's login is Keychain-only; (c) E7/E12 and the kill/escape test on the real CLI. Final verdict waits for #19.

## Proposed effect on the architecture (for task 4.2)
- §4 Fit table, gemini slot: CLI = Antigravity `agy` 1.5.x (the Gemini CLI is reported unsupported by Google); headless = `agy -p "<prompt>" --output-format json --model <id>` inside the outer profile only, with `enableTerminalSandbox:false` and either `--dangerously-skip-permissions` (used in every run here, but allow/deny under it is untested) or `permissions.allow` rules (part B to decide); credential = file `$HOME/.gemini/antigravity-cli/antigravity-oauth-token` (0600 JSON, access + refresh token) created by `agy acp --login` inside a sandboxed Step, then copied read-only into each Step; refresh = in memory per call (needs `oauth2.googleapis.com`), no probe needed for ~1 h expiry (refresh-token lifetime over days, revocation and parallel refresh not measured; a probe may still be wanted for those) (needs a `D-` entry because ADR-004/ADR-005 and D-63 name the Gemini CLI and assume a copy of the owner's existing credential).
- §5: Mach allowlist for agy = `com.apple.trustd.agent`; extra non-Mach rules: `/etc/hosts` read, loopback `network-inbound`, and for the builder shape `/bin/zsh` exec + PTY device files (the PTY rule matches every pseudo-terminal of the machine, including the owner's terminals: carry that cost into §5); gateway allowlist = `daily-cloudcode-pa.googleapis.com`, `aicode.googleapis.com`, `www.googleapis.com`, `oauth2.googleapis.com` (telemetry host `play.googleapis.com` and avatar host `lh3.googleusercontent.com` denied).
- §19: Q1 (Keychain-free credential) answered for `agy` by the file token store; Q2 (refresh) answered (in-memory per call, ~1 h access token); Q3 partly (own sandbox: off by default, pin `enableTerminalSandbox:false`); Q4/Q5 wait for part B.
