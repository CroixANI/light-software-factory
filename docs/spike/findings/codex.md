# codex, part A: E1–E5 (task 3.3, issue #16)

Evidence: [spike/codex/](../../../spike/codex/) (`run-codex.sh`, `codex.sb`, `shell.sb`, `part-a.sh`, `logs-part-a.txt`). Plan: [../plan.md](../plan.md). Part B (E6–E12, S1–S5 re-run) is task 3.4 (issue #17) and is appended to this file.

## Setup
- macOS 27.2.1 (arm64); codex-cli 0.171.0 (native Mach-O binary in `~/.codex/packages/standalone/releases/0.171.0-aarch64-apple-darwin/bin/`, symlinked from `~/.local/bin/codex`; the launcher resolves it and grants read + exec on that `bin/` directory only; nothing else of the install was needed).
- Credential: the owner's ChatGPT login, a **file** `$CODEX_HOME/auth.json` (`auth_mode: chatgpt`; fields `tokens.{id_token, access_token, refresh_token, oauth_provenance, login_owner_id, account_id}`, `last_refresh`; ~4 KB). Copied into `<step>/home/.codex/auth.json` as mode 0400 by `lib.sh step`; `codex.sb` additionally denies `file-write*` on that one path. Never printed or committed; the step copy was byte-identical to the source after a checked run (`cmp`, one run; the file is write-protected by the profile in all runs). The copies lived in a scratch directory outside the repository and were removed afterwards.
- Step folder from `build-step-folder.sh`, a gateway from `connect-proxy.mjs --port <p>` (one per run, to get a clean host list). Profile: `base.sb` + `codex.sb` (+ `shell.sb` for shell-tool runs) + one `mach-lookup` rule: `com.apple.system.opendirectoryd.libinfo` (see E3).
- Environment (empty + allowlist): `PATH=/usr/bin:/bin`, `HOME=<step>/home`, `CODEX_HOME=<step>/home/.codex`, `TMPDIR=<step>/tmp`, `LANG`, `TERM=dumb`, `HTTP(S)_PROXY=http://127.0.0.1:<port>`, `FACTORY_STEP`, **`CODEX_CA_CERTIFICATE=/private/etc/ssl/cert.pem`** (E3: needed to avoid the Keychain daemon).
- Prompt on stdin. Base command (`R=spike/codex/run-codex.sh`, `S` = step folder, `perl -e 'alarm 90; exec @ARGV'` as wall clock, macOS has no `timeout`):
  `$R --step $S --port 8941 --env CODEX_CA_CERTIFICATE=/private/etc/ssl/cert.pem --mach com.apple.system.opendirectoryd.libinfo -- exec --json --skip-git-repo-check -s read-only [-c 'cli_auth_credentials_store="file"']`
- `spike/codex/part-a.sh` re-runs E1, E3, E4 and E5 with fresh Steps (output: `logs-part-a.txt`); E2 uses `mutate-auth.py` (commands below).

## Results
| # | Result | Evidence |
|---|---|---|
| E1 Keychain-free credential | **pass** | Unsandboxed with an isolated `HOME`/`CODEX_HOME` and then under the full `(deny default)` profile with zero Keychain/security Mach services: the call completes (`turn.completed`, one `agent_message`). Without `auth.json` in the Step: the run fails (rc 1) with `401 Unauthorized: Missing bearer or basic authentication` on `wss://api.openai.com/v1/responses` after five reconnects, so there is no other credential source (the owner's Keychain is unreachable under the profile; the unsandboxed no-file case was not run, so "no Keychain fallback" is shown only under the profile). The default store is already `file` (the owner's `config.toml` does not set it); pinning `-c cli_auth_credentials_store="file"` works too and belongs in the adapter's flags. |
| E2 Credential refresh | **recorded; real refresh not run on purpose** | The `access_token` JWT had `exp` ≈ 240 h after `iat` (10 days), the `id_token` ≈ 1 h; the owner's live `auth.json` had a `last_refresh` of the same minute when first read (so something, probably the owner's Codex app, refreshes it often; not investigated). With mutated copies (`mutate-auth.py`, **refresh token always replaced by a dummy**, so a refresh can only fail and cannot rotate the owner's real one): (a) `last_refresh` 30 days old, valid access token → no refresh attempt (no `auth.openai.com` in the gateway log), call completes; (b) access-token signature destroyed → `401 Could not parse your authentication token`, then **one** CONNECT to `auth.openai.com:443` (the refresh attempt), then rc 1 and `Your access token could not be refreshed. Please log out and sign in again.` (class: auth/credential, see E12 in part B). Why no real refresh: OpenAI refresh tokens appear to rotate, and the owner's file is shared with their Codex app, so burning it from a Step copy could log the owner out; whether it rotates was **not** verified. **Consequences for the adapter (proposals):** (1) the Step copy should carry a dummy `refresh_token` (tested in (a): works) so a Step can never consume the real one, and the read-only file cannot persist a refresh anyway; (2) refresh happens only in `provider probe` against the real `CODEX_HOME`, not in a Step; (3) the access token lives ~10 days, so a Step started right after a probe is not at risk. **Open (part B / owner):** what the probe command is (`codex login status` prints `Logged in using ChatGPT`; whether it validates the token against the server was not checked, and a model call as the probe was not tried), whether a successful refresh rotates the refresh token, and what happens to the owner's Codex app when `auth.json` is rewritten under it. |
| E3 Mach allowlist | **pass: one service, with one condition** | Allowlist = **`com.apple.system.opendirectoryd.libinfo`** (a candidate already listed, not added, in [MACH-SERVICES.md](../../../spike/harness/sandbox/MACH-SERVICES.md)) **and `CODEX_CA_CERTIFICATE=/private/etc/ssl/cert.pem`**, with a read rule for that file. (1) With **no** Mach rule the CLI aborts at start: `failed to load configuration: Failed to synchronize managed preferences (code -32600)`; `libinfo` alone fixes it (6 of 6 runs with fresh or reused Steps). (2) **Without the CA variable** TLS verification (platform verifier) fails against the gateway: the TLS handshake is aborted after ~170 bytes up (`ECONNRESET` in the gateway log, 66 CONNECTs in one run, rc 1) with `libinfo` (+ `trustd.agent`); it works only after `com.apple.SecurityServer` (the Keychain daemon) is added (`libinfo` + `trustd.agent` + `SecurityServer`, 3 runs). `SecurityServer` is excluded by the plan, so the CA bundle variable is **mandatory**, not an optimisation. (3) `com.apple.cfprefsd.agent` is tolerated; adding **`cfprefsd.daemon` made the managed-preferences error come back** (2 runs; cause not investigated). (4) The CLI also reads `/etc/codex/requirements.toml` (admin policy); under the profile that read gives `EPERM` and aborts the start (`Failed to read requirements file … Operation not permitted`), so `codex.sb` allows reading that path (absent here → ENOENT; on a managed Mac it would be applied, which is wanted). (5) The shell tool runs `/bin/zsh -lc '<cmd>'` (login shell, `SHELL` unset): `/bin/zsh` needs an exec rule in builder-like profiles, not only `sh`/`bash`. Excluded and untouched: launchd job submission, LaunchServices, Apple Events, Keychain/`security` services, pasteboard; `mach-register`, `iokit-open`, `ipc-posix` stay denied. **Method and limits:** denial lines are not readable without root, so services were found by a bisect: `(allow default)` + `(deny mach-lookup)` + candidates (`min-mach.sh`), then confirmed under the real profile. The allow-default minimisation reported `cfprefsd.agent` as needed too; the real profile did not need it, so the real-profile runs are authoritative and `min-mach.sh` is only a candidate finder. `dotnet`/`node` under codex's shell tool were **not** re-run; [sandbox-s5.md](sandbox-s5.md) showed zero Mach rules for them. Why `libinfo` is needed (managed-preferences lookup of the user directory) is inferred from the error text, not traced. Cost of `libinfo`: lets the worker query the user/group directory (see MACH-SERVICES.md). |
| E4 Proxy compliance | **pass, with a limit** | The gateway log of a run with default flags: `chatgpt.com:443`, `ab.chatgpt.com:443` (feature flags/analytics), two `sdmntpr*.oaiusercontent.com:443` hosts (plugin/app assets). With `--disable plugins --disable remote_plugin --disable apps --disable in_app_updates -c analytics.enabled=false` the only host is **`chatgpt.com:443`** (3 runs: ≈5 CONNECTs, ≈14 KB up); the two asset hosts went away with the plugin/apps switches and `ab.chatgpt.com` with `analytics.enabled=false` (a run with the plugin switches but without the analytics one still contacted it). The transport is a WebSocket (`wss://chatgpt.com/…`, falling back to HTTPS) through `CONNECT`, so `HTTPS_PROXY` is honoured. A refresh adds `auth.openai.com:443` (E2); in API-key mode the host would be `api.openai.com` (seen in the no-credential run). Earlier allow-default (unsandboxed-network) runs also reached `api.openai.com`, `api.github.com`, `codeload.github.com` and `files.openai.com` (curated-plugin sync, file downloads); they never appeared in a sandboxed run with the switches above. Dead gateway port (nothing listens on 8999): no direct connection is possible, the CLI retries (`Reconnecting… 2/5 … workspace routing discovery failed`) and exits **rc 1 after ≈22 s**: it does not hang until the wall clock as claude did. Second source: 40 samples (250 ms) of `lsof -i` on the CLI process during a normal run show only `127.0.0.1:<gateway port>` sockets. **Limits:** the profile allows only `localhost:<port>` and no Mach lookup, so a direct attempt would be dropped silently and not appear in the gateway log; the `lsof` sample can miss a short-lived socket; the gateway allowlist for a Step is therefore `chatgpt.com` (plus `auth.openai.com` for the probe), but only with the switches above set. |
| E5 Own sandbox off | **pass** | Setting: `-s danger-full-access` together with `-c approval_policy="never"` (equivalent: `--dangerously-bypass-approvals-and-sandbox`, also tested). The shell tool then runs inside the outer profile (`/bin/zsh -lc 'echo hello-from-shell'` → exit 0). With the CLI's own sandbox on (`-s workspace-write`) inside our profile the shell tool fails: `exec_command failed … Operation not permitted (os error 1)` (a nested Seatbelt cannot be applied inside ours; same with `/usr/bin/sandbox-exec` exec-allowed), so nothing is nested and nothing runs. Outer profile stays in charge with the CLI sandbox off: a shell write to `../OUTSIDE-TEST` was denied (`Operation not permitted`), a write inside `repo/` worked (profile = `shell.sb`). Approval flags: `never` means no prompts in `exec`; a denied-tool case was **not** tested. The CLI has no per-command allow/deny flag besides execpolicy rules (`--ignore-rules` exists) and feature toggles: `codex features list` shows `shell_tool` (stable, on) which `--disable shell_tool` should switch off (not run; E10, part B). **Adapter risk (the safe direction):** if a config file turns `workspace-write` back on, the shell tool simply fails under our profile; it cannot escape. The CLI warns `Untrusted project-local configuration is disabled` on every start (no `.codex/` was planted in part A, so what it ignores is E8, part B); `--trust` must never be passed. |

## Other findings
- **Repository instructions are read:** in the E5 runs the model echoed the planted `AGENTS.md` canary (`CANARY-AGENTS-MD`) although nothing asked for it. This is E8 (part B); noted here because it affects every Step: the adapter must exclude instruction files from the copy or find a flag.
- `home/.codex/` after a run holds `sessions/`, `state_5.sqlite*`, `logs_2.sqlite*`, `goals_1.sqlite*`, `memories_1.sqlite`, `queue_1.sqlite*`, `thread_history_1.sqlite`, `models_cache.json` (~177 KB, fetched over the gateway), `installation_id`, `plugins/`, `skills/`, `cache/`. State carries over only through `home/` (E9, part B; `--ephemeral` exists).
- With `--json` stdout is JSONL events (`thread.started`, `turn.started`, `item.completed`, `turn.completed` with `usage.{input_tokens, cached_input_tokens, output_tokens, reasoning_output_tokens}`); usage per call was ~13 000 input tokens (10 752 cached) for a one-word answer. E6/E7 are part B.
- The owner's `config.toml` sets `model = "gpt-5.3-codex"` and `model_reasoning_effort = "xhigh"`; Steps start with an empty `CODEX_HOME`, so the adapter must pass model and effort itself (E6, part B).
- zsh note for harness authors: `$RANDOM`/counters inside `$(…)` do not persist (a first set of runs silently reused one Step folder); use a unique id per run.

## Verdict for part A
E1, E3, E4, E5 pass for `codex`; E2 recorded, with the real refresh deliberately not run. No `unsupported` condition of D-63 is met. **Condition:** E3 passes only with `CODEX_CA_CERTIFICATE` set and readable and `libinfo` allowed; if either is dropped the CLI needs the Keychain daemon (`SecurityServer`) and E3 fails. The final verdict waits for part B (#17).

`python3 -I spike/codex/mutate-auth.py ~/.codex/auth.json <step>/home/.codex/auth.json old-last-refresh|bad-access-token` (writes a 0400 file, prints no token), then the base command above with a gateway on its own port.

## Proposed effect on the architecture (for task 4.2; `decisions.md` is not edited here)
- §4 Fit table, codex: headless = `codex exec --json -s danger-full-access -c approval_policy="never" -c cli_auth_credentials_store="file" --skip-git-repo-check --disable plugins --disable remote_plugin --disable apps --disable in_app_updates -c analytics.enabled=false`, prompt on stdin (model/effort/schema flags: part B); credential = the owner's ChatGPT `auth.json` copied read-only into `<step>/home/.codex` **with a dummy `refresh_token`** (a departure from "copy the file as is" in ADR-005, needs the owner's decision); refresh = probe only, ~10-day access token.
- §5: Mach allowlist for codex = `com.apple.system.opendirectoryd.libinfo` only (Keychain stays excluded because the CA bundle is supplied); env allowlist additions `CODEX_HOME`, `CODEX_CA_CERTIFICATE`; read rules for `/etc/codex/requirements.toml` and `/etc/ssl/cert.pem`; exec rule for `/bin/zsh` in the builder shape; gateway allowlist = `chatgpt.com` (+ `auth.openai.com` for the probe).
- ADR-005: the credential is a file, so this CLI fits the ADR text better than claude's token-in-env route; the dummy-refresh-token change is the only departure.
