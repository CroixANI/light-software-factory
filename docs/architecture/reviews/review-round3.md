## 3. New findings (introduced by revision 3)

### C1 — `requests` now counts gateway connections, which undercounts provider use and breaks the provider threshold
- **Severity:** Important. **Lens:** 4 and 5.
- **Evidence:** `arch:409` redefines `requests` as "connections to provider hosts counted by the gateway, so always measured". `arch:171` and `ADR-005:36` call these connections "the Step's always-measured `requests`". The gateway is a CONNECT proxy (`arch:170`), so it sees TLS tunnels, not HTTP requests. A single kept-alive HTTP/2 connection carries a whole session. The provider threshold (`arch:418`) compares "observed use" with window limits such as Gemini's **requests/day** quota (`facts:20`), and `arch:129` takes that quota from the CLI's own stats.
- **Conflicts with:** D-60 (metered and charged), D-19 provider threshold (`decisions.md:143`), value 5 (the label does not match what is measured).
- **Impact:** A Step that makes hundreds of provider requests over one connection is charged `requests = 1`. Budgets on `requests` never refuse, the threshold under-reports Gemini quota, and the D-60 charge is nominal.
- **Fix (local edit):**
  1. Keep `requests` as the CLI-reported count; it may be `not measured`.
  2. Add `gateway_bytes` (and `connections`) as the always-measured dimension, and charge D-60 traffic by bytes, with a per-provider bytes-to-tokens estimate taken from the journal and flagged `estimated`.
  3. Have the threshold use CLI-reported requests where available, and otherwise the byte-based estimate, labelled as such.

### C2 — An approved `suppressions` rise has no path through `checking`, and after merge it turns main red for everyone
- **Severity:** Important. **Lens:** 4 (introduced by the A5 and B4 fixes).
- **Evidence:** In `checking`, the ratchet fails on any rise (`arch:247`, `arch:608`). The human diff approval for a `suppressions` rise is requested only at `pr_open` entry (`arch:249`, `arch:369`), which the item cannot reach while `checking` fails. Without that approval, the item loops between `checking` and `building` until "same failure twice → parked" (`arch:247`). If a human approves anyway (for example from `parked`) and the PR merges, main's `suppressions` sits above the effective baseline. That baseline is the stricter of the file and the best value on main (`arch:608`), so an approved rise never moves it. Then `main_gate` runs the same ratchet and fails, which pauses group dispatch (`arch:250`). Every later item, built from main, fails too. The closing PR also writes the stricter value (`arch:331`), so main stays red after close.
- **Conflicts with:** A5 / §8 "can be accepted by a human diff approval" (`arch:369`, `arch:608`); D-37 green gate on main (`decisions.md:269`).
- **Impact:** One justified suppression stops the group.
- **Fix (local edit):**
  1. In `checking`, record a `suppressions` rise as `pending approval`, not as a failure, and let the item continue to `reviewing` and the approval at `pr_open`.
  2. An approved rise, which is a board `approval` entry bound to the SHA, raises the effective baseline for that metric to the approved value. The gate on main and later items use that value.
  3. The closing PR writes the effective baseline including approved rises.

### C3 — How a new run adopts unfinished items is not specified (Nit)
- **Evidence:** `arch:315`: "A re-plan creates a new run that adopts the unfinished items in their current states." Not defined: whether an adopted item continues under the **new** config snapshot mid-flow; whether its plan approval, which is bound to the old plan hash and base SHA (`arch:254`), stays valid; and how its run- and group-scope reservations (`arch:411`) move to the new run.
- **Fix:** Adopted items go back to `planning` (plan kept, critique and approvals re-run against the new snapshot), or stay pinned to the old snapshot. State which, and move the reservations in the same transaction.

### C4 — It is not defined whether a Step's edits are applied when it ends `blocked` (Nit)
- **Evidence:** `arch:149` discards the edits of Steps that ended with `needs_context` or failed, but does not say what happens on `blocked`. The new path `blocked: dependency` (`arch:108`, `arch:246`) makes this matter. Applying a partial build commits half an implementation before re-planning; discarding throws away work.
- **Fix:** Discard the edits on `blocked`, as for `needs_context`, and say so in §5 step 5.
